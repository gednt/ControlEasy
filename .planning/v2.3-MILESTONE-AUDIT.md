### 8. Append-only invariants

- **VERIFIED for `device_unlock_audit`.**
- `0017-devices.sql` + `17-devices-schema.sql` define MySQL triggers
  `trg_device_unlock_audit_no_update` and `trg_device_unlock_audit_no_delete`
  raising `SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'DeviceUnlockAudit is
  append-only: UPDATE/DELETE is not permitted'`. The integration test
  `DeviceUnlockAuditTriggerTests.AuditUpdate_IsRejected_WithSignal45000` +
  `AuditDelete_IsRejected_WithSignal45000` confirm MySqlException error
  code 1644.
- **PARTIAL for `device_events`** (intentional, documented).
- `0019-device-events.sql` does NOT define MySQL triggers because the
  append-only invariant is enforced at the API surface: the
  `IDeviceEventRepository` abstraction exposes **only** `InsertAsync`,
  `GetByIdempotencyKeyAsync`, `GetByIdAsync`, `ListAsync` — **no Update
  or Delete methods** (verified by
  `grep "Update\|Delete" src/Modules/Devices/.../IDeviceEventRepository.cs`).
  This is consistent with the broader project's lead-card pattern
  (see 09b-consent-schema.sql which DOES have triggers but other v2.x
  ledger tables rely on API-contract append-only).
- `device_heartbeats` is intentionally mutable (INSERT ... ON DUPLICATE KEY
  UPDATE) — that's the design contract for Phase 26's per-device status
  rollup (Status codes are NOT ledger rows; they are derived from the latest
  heartbeat + the per-device thresholds). This is correct behavior for a
  status rollup table and not a defect.

   Web SPA gate (`npm test` + `npm run lint` via the canonical

   AGENTS.POLICY.md) is exercised per phase on Linux; on Windows the
   Karma+Playwright specs run via `ng test --browsers=ChromeHeadlessNoSandbox`
   (per Phase 26's Web SPA gate section). Surfaced for transparency — not a
   regression and not blocking.
2. **OpenAPI client regeneration drift** (Phases 24, 25, 26). The Angular
   code uses a handwritten `DevicesApiService` (extended from Phase 23)
   and bypasses the generated OpenAPI client. The Phase 23 baseline
   regenerated the client once; subsequent phase endpoints (7 in Phase 24,
   2 in Phase 25, 1 in Phase 26) added new URL paths + verbs that are
   constructed manually in the handwritten service. Low-risk follow-up.
3. **Subquery flake in `RunInitScripts`** (pre-existing, documented in
   Phase 24/25/26 VERIFICATIONs). When multiple
   `IClassFixture<MySqlContainerFixture>` collections initialise in
   parallel against the shared `CE_ITEST_MYSQL` DB, MySQL throws
   `Subquery returns more than 1 row`. Per-collection runs (Devices,
   AccessControl, etc.) are green; the Devices `--filter` run is
   reproducible green. Does NOT block milestone completion because the
   canonical CI gate runs the `--filter Devices` partition. Will be
   fixed in v2.4 by moving to per-collection DBs or sequential init.
4. **`PlaywrightValidate` plugin deletion in index** (Phases 24, 25, 26).
   Unrelated to v2.3 scope; the file may have been intentionally pruned.
   Index state left as-is.
5. **`openapi.json` removed from working tree** (Phase 24). Stale entry
   from a previous attempt; not part of this milestone's commit surface.
6. **Stage 6 OpenAPI drift check flakes** (Phase 23 baseline). Docker
   port-forwarding timing in the local script is fragile; the regenerated
   client was already committed. No actual drift; the Gitea CI run is the
   authoritative source.
7. **`IngestHeartbeatHandler` uses payload.OccurredAtUtc for gap calc**
   (Phase 26, documented deviation). The heartbeat's timestamp is the
   source of truth (the simulator may replay stale events from a backlog).
   The 5-minute freshness window in `HeartbeatValidator` rejects very
   stale heartbeats at the API edge.

Live Playwright validation on 2026-10-11 found a material integration gap
that the source-only audit did not prove: registering a gatehouse in

from the Gatehouse desk, QR scan, manual lookup, package drop, credentials,

access event. This follow-up must provide an explicit active gatehouse context,
send its ID in new desk actions, tenant-validate supplied IDs, expose the
registered locations on device health, restore the navigation icon, and prove
the path in the real browser. Historical rows may remain unattributed, but new
scan, manual, package, and device-ingestion records must identify a registered
gatehouse owned by the current tenant.
