<objective>
Close the last raw-UTC summary path in the Reports module (LEDGER-01, INFRA-02 closeout).

Purpose: `GetVisitCountsByDayAsync` still buckets the daily visit-count summary by raw UTC
instead of the tenant's local day boundary. This makes the "Daily visit volume" card disagree
with the unified ledger near midnight. The ledger history path (`GetHistoryHandler`) already
normalizes via `TenantDayBoundary`; this plan makes the summary path follow suit so the
reports surface tells one honest story.

Output: A `ToTenantDate(DateTime utc)` helper on `TenantDayBoundary`, a
`ReportReadRepository.GetVisitCountsByDayAsync` that (a) normalizes its `from`/`to` range and
(b) buckets each row by tenant-local date, plus unit and integration tests proving the bucket.
</objective>

  <files>src/Modules/Reports/ControlEasyReborn.Modules.Reports.Application/Time/TenantDayBoundary.cs, src/Modules/Reports/ControlEasyReborn.Modules.Reports.Infrastructure/Persistence/ReportReadRepository.cs, tests/ControlEasyReborn.IntegrationTests/ReportEndpointTests.cs</files>
  <action>
Per LEDGER-01 (INFRA-02 closeout): make `GetVisitCountsByDayAsync` bucket visit counts by the
tenant's local day boundary, not raw UTC, reusing the existing `TenantDayBoundary` helper
(already used by `GetHistoryHandler` for the ledger). Do NOT hand-roll timezone math, and do NOT
guess the tenant midnight on the client — bucketing must stay server-side.

Two changes in `TenantDayBoundary.cs` and `ReportReadRepository.cs`, plus one integration test:

1. In `TenantDayBoundary.cs`, add a public static helper
   `public static DateOnly ToTenantDate(DateTime utc)` that converts a UTC timestamp to the
   tenant-local calendar date. It must reuse `ResolveTimeZone()` (do not duplicate the
   timezone-resolution logic). Implementation shape: convert the input UTC DateTime through
   `TimeZoneInfo.ConvertTimeFromUtc` using the resolved zone, then `DateOnly.FromDateTime` of the
   resulting local DateTime. Preserve the existing `DefaultTimeZoneId` ("America/Sao_Paulo"),
   the Windows fallback, and the fixed-offset fallback — no per-tenant timezone config this phase
   (per CONTEXT deferred list).

2. In `ReportReadRepository.cs`, fix BOTH halves of the raw-UTC bug (partial fix is the trap —
   RESEARCH Pitfall 1):
   a. `BuildDateRangeClause(DateOnly? from, DateOnly? to, out object[] parameters)` currently
      emits `CreatedAtUtc >= @paramN` with `from.Value.ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc)`
      and `CreatedAtUtc < @paramN` with `to.Value.AddDays(1).ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc)`.
      Replace those two parameter values with tenant-local bounds mirroring `GetHistoryHandler`:
      `from` → `TenantDayBoundary.GetDayBoundsUtc(from.Value).StartUtc`, and
      `to` → `TenantDayBoundary.GetDayBoundsUtc(to.Value.AddDays(1)).StartUtc` (inclusive end day).
   b. `MapVisitDate(DataRow row)` currently returns `DateOnly.FromDateTime(Convert.ToDateTime(row["CreatedAtUtc"]).ToUniversalTime())`.
      Replace the body with `TenantDayBoundary.ToTenantDate(Convert.ToDateTime(row["CreatedAtUtc"]))`
      so each row buckets into its tenant-local date, not the raw UTC date.
   Add the `using ControlEasyReborn.Modules.Reports.Application.Time;` directive to
   `ReportReadRepository.cs` (it is not currently imported).

3. In `tests/ControlEasyReborn.IntegrationTests/ReportEndpointTests.cs`, add a new `[Fact]` (e.g.
   `GetVisitCountsByDay_BucketsOffMidnightUtcVisitToTenantLocalDay`) that seeds a visit with a
   `CreatedAtUtc` value that falls on a DIFFERENT tenant-local day than its UTC date — e.g.
   `2026-09-19T02:00:00Z` (≈ `23:00` São Paulo on `2026-09-18`). Use a direct MySQL UPDATE (like the
   existing `History_pending_visit_checked_in_today_shows_on_today_at_checkin_timestamp` test does)
   to backdate the seeded visit's `CreatedAtUtc` to that off-midnight UTC timestamp, then assert the
   `GET /api/v1/reports/visit-counts-by-day` response contains a bucket for the tenant-local date
   `2026-09-18` and does NOT mis-file it under `2026-09-19`. Do NOT write a test that only asserts
   "rows returned, non-empty" (the existing `GetVisitCountsByDay_ReturnsAggregatedRows` already does
   that and would pass even when bucketing is wrong — RESEARCH Pitfall 1 warning sign). Assert the
   specific bucket date. Use synthetic data (no real names/documents).
  </action>
