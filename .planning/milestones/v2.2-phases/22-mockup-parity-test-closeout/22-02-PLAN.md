<objective>
Close the remaining login functional-fix gap per UI-02 (locked decision: "login form behavior, toast patterns, page interactions — real error paths, submit spinner, auto-dismissing toasts"). The login page ALREADY implements most of the `.specs/2-mockup-functional-fixes/` contract: real 401 error path (`extractErrorMessage` → "Invalid email or password."), submit spinner via `ce-button [loading]`/`aria-busy`, password show/hide, tenant picker for multi-tenant emails, and demo/boot accounts. The single genuine gap is the forgot-password flow: on success it renders an inline `forgot-success-banner` in the modal, whereas the mockup contract (`login.html` + UC-11) surfaces an info toast "Check your email for reset instructions".

Purpose: make the forgot-password success signal follow the ToastService pattern the rest of the app uses (auto-dismissing, tone-coded, aria-live) instead of a bespoke inline banner, and lock the login behaviors with unit tests.

Output: login page emits an info toast on forgot-password success (keeping the inline banner only as a fallback-free removal target), with unit tests covering 401 inline error, submit busy state, and forgot-password toast parity.

**Surface (decision, not silently picked — RESEARCH Assumptions A2 + A3):** (1) The current inline success banner is arguably better UX; converting it to a toast is a parity call, and the plan converts to the toast (the locked mockup contract) while keeping the modal's explanatory hint text. (2) The mockup's fake `ratelimit@x.com` 15-second 429 cooldown may NOT map to a real backend behavior — the Angular side must mirror whatever the backend actually returns, not the mockup's hardcoded demo. The plan does NOT invent a client-side 15s cooldown; it only ensures the 429 detail is surfaced through the existing enumeration-safe error path. If the backend does not emit 429 for login, no client cooldown is added.
</objective>
