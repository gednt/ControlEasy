# Requirements: ControlEasy Reborn — Milestone v2.5

**Defined:** 2026-09-23 (v2.5 planning session — BMAD party-mode hardware-research follow-up)
**Core Value:** Gatehouse staff can reliably register and control access through a fast, tenant-isolated web UI.

## v2.5 Requirements

**Real Vendor Hardware Integration.** v2.3 builds the complete door-integration machinery — `IDoorController`/`IDeviceHandler` abstractions, unlock security, event pipeline, health monitoring — against a simulated device adapter. v2.5 makes it real with three first-party vendor drivers: **Control iD**, **Intelbras**, and **Hikvision** — chosen by Felipe (2026-09-23) from the research gold-signal list (Intelbras, Control iD, Henry, Hikvision, Nice, Garen — vendors cross-validated by SaaS portaria-platform integration lists). Two of the three (Intelbras connect-and-subscribe, Hikvision ISAPI) are we-dial-the-device surfaces behind CGNAT, which forces the **edge agent** — a small on-site runtime with a single outbound-only channel — into the milestone. All three drivers ride the agent (one channel, one credential story). **Zero physical hardware in CI**: every vendor surface has a simulator exercised by the integration suite; real-device verification happens only at the on-site pilot (DOOR-R3).

**Constitutional security bar (applies throughout):** the v2.3 door security machinery applies identically to real drivers — HMAC-SHA256 per-tenant key, nonce + timestamp replay window, rate limit (max 1 unlock per 3 seconds per device), append-only tamper-evident audit, AES-256-GCM-encrypted connection params, porteiro-role authorization — proving it vendor-agnostic. No EF Core — DBTools only; no MediatR; minimal API endpoints; all tenant-scoped reads/writes via `ITenantAwareLinqFactory`; `ProblemDetails` (RFC 7807); Serilog. The edge agent is a new deployed component inside the condominium: per-agent credentials, no inbound ports, VLAN isolation for device networks (mandatory for Hikvision given its CVE history), vendor device credentials never in logs or plaintext persistence.

### Edge Agent & Driver Foundation

- [ ] **HW-01**: Edge agent runtime — a small Docker container deployed on-site connects outbound-only (WSS) to the cloud API; no inbound ports are opened (CGNAT-compatible); each agent authenticates with a per-agent credential issued at provisioning; agent link status rides `device_heartbeats` so a dead agent surfaces in the health dashboard (DOOR-13)
- [ ] **HW-02**: Local event queue with idempotent replay — events from we-dial-them devices queue locally with per-device sequence numbers and replay on reconnect; dedupe is idempotent (no event lost, none double-processed — extends DOOR-11 to real hardware), `processed_at` vs `occurred_at` preserved
- [ ] **HW-03**: Vendor contract-test harness — simulators for each vendor surface (Control iD REST + webhook mock, Intelbras connect-and-subscribe mock, Hikvision ISAPI mock with digest auth + alert stream) are exercised by the integration suite with zero physical hardware (no hardware in CI, ever)
- [ ] **HW-04**: Real-device provisioning — a TenantAdmin registers a device choosing vendor + model profile (Control iD, Intelbras, Hikvision); per-vendor connection params are validated, AES-256-GCM-encrypted at rest (rides DOOR-04/DOOR-06), and bound to an agent for we-dial-them devices

### Vendor Drivers

- [ ] **HW-05**: Control iD driver (first real integration — DOOR-R1) — `IDoorController` unlock via the public Access API (remote door/turnstile release, LAN or Push mode); `IDeviceHandler` ingests device-push notifications (access logs, catraca turn confirmations, `device_is_alive` heartbeats) normalized to `DeviceEvent`; card-match → ledger entry, unknown card → denied attempt (rides DOOR-08..10); HTTPS support for device callbacks verified (research flagged it UNVERIFIED — if absent, the callback path is documented as agent-relayed with the risk stated)
- [ ] **HW-06**: Intelbras driver (second integration — proves the abstraction, DOOR-R2) — edge-agent-resident: connect-and-subscribe event ingestion per the official integration API (doc V1.3, 2020 — no webhook push; firmware-generation quirks documented); relay actuation for unlock; every endpoint verified against the actual device or vendor-confirmed doc before sign-off
- [ ] **HW-07**: Hikvision driver (third integration) — edge-agent-resident: unlock via the ISAPI door-command family with digest auth; events via the alert-stream subscription; deployment requires documented VLAN isolation — never internet-facing (CVE history); partner-portal doc access requested in Phase 31 so it is unblocked by Phase 34
- [ ] **HW-08**: Security-bar parity — every real driver passes the same unlock security machinery as the v2.3 simulator (HMAC, replay window, rate limit, audit); the v2.3 unlock/event integration suites run against each vendor simulator unchanged — vendor-agnostic behavior proven, not assumed

### Pilot & Closeout

- [ ] **HW-09**: On-site pilot verification (DOOR-R3) — at a pilot condominium with real hardware of at least one supported vendor: card reader + manual release operate with the API down (participant, not gatekeeper), missed events replay on reconnect, unlock latency acceptable, the health dashboard reflects real devices; findings recorded in a pilot report

## Out of Scope

| Feature | Reason |
|---------|--------|
| Henry driver in v2.5 | No official docs — community-reverse-engineered protocol; second wave after the three research-verified vendors |
| Gate-motor relay tier (Shelly et al.) in v2.5 | Validated by research but not in Felipe's v2.5 vendor pick; second wave |
| ZKTeco, Alphadigi, Bravas, dormakaba, HID/Mercury, Nedap, Genetec | Partner-NDA or single-source evidence; revisit when a paying condominium shows up with the hardware |
| Direct cloud→LAN exposure (VPN/port-forward) | CGNAT-heavy Brazilian ISPs; no modern vendor does it; rejected by research |
| OSDP termination in the cloud | Reader↔controller bus protocol — wrong layer; the cloud never speaks OSDP |
| ONVIF Profile A/C drivers | Thin real-world adoption in Brazilian budget controllers; vendor APIs are the real surface |
| Biometric template storage | No biometrics in v2.5; card/credential events only (FUT-01) |
| Physical hardware in CI | Vendor simulators only; real hardware at the on-site pilot (HW-03, HW-09) |
| Control iD direct-to-cloud (bypassing the agent) | One channel for all drivers; revisit in Phase 31 discussion only if the pilot demands it |
