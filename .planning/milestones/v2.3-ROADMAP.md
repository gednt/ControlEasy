## Overview

The complete **hardware-independent** portion of the door-integration spec (`.specs/door-integration/`), built simulator-first because real condominium hardware does not yet exist. v2.3 delivers:

- `IDoorController` / `IDeviceHandler` vendor-agnostic abstractions, with in-process simulator implementations
- The full **security machinery** for remote unlock: HMAC-SHA256 per-tenant signing (HKDF-derived keys), nonce + timestamp replay window, per-device rate limiting (1 unlock / 3s), porteiro-role authorization, append-only tamper-evident audit, AES-256-GCM connection-params encryption per tenant
- The **reader-event → ledger pipeline** with a strict single-write-path doctrine: Devices module never instantiates Visit / AccessEvent / RefusedScanAttempt entities; every ledger write flows through the existing `VisitorArrivalHandler` / `RecordAccessScanHandler` / `RecordRefusedScanHandler` machinery
- Idempotent event replay on disconnect via MySQL `UNIQUE (tenant_id, device_id, sequence_number, external_event_id)` translated from errno 1062 → `DuplicateIdempotencyKeyException`
- **Device health monitoring**: `device_heartbeats` per-device upsert with derived `online/offline/degraded` status, dashboard page, gatehouse-panel offline toast on transition edges
- Admin + Porteiro Angular surfaces: `/administration` Door Integration section (opt-in toggle + device list + disabled card + standalone modal), `/devices` health dashboard, gatehouse-panel inline ce-toast

Real vendor drivers and on-site hardware verification stay out until hardware exists — concretized as milestone **v2.5** (Control iD Phase 32 → Intelbras Phase 33 → Hikvision Phase 34 + edge agent + on-site pilot).

## Milestone Summary

**Decimal Phases:** None — all 4 phases were integer (23, 24, 25, 26).

**Key Decisions:**

- v2.3 simulator-first re-scope (2026-09-22): the original Phases 14–15 reservations assumed real hardware that does not exist; reservations retired, phase numbering continues from 23. Real vendor driver work stays out until hardware exists.
- `IDoorController` emerges from Phase 23 directly (vs `IDeviceHandler` from a 2nd integration); the unlock path is the highest-risk surface, and HMAC discipline over APM-shipping guarantees matter for the security bar.
- The security bar (HMAC-SHA256, nonce + timestamp replay window, rate limiting, tamper-evident audit, AES-256-GCM connection params, porteiro-role authorization) is the v2.3 contract; vendor drivers in v2.5 must ride it, not bypass it.
- Single-write-path doctrine for reader events: zero new Visit / AccessEvent / RefusedScanAttempt entities in `src/Modules/Devices/`; every ledger write flows through `RecordAccessScanHandler` / `RecordRefusedScanHandler` / `VisitorArrivalHandler`. Enforced by code grep in the audit.
- Idempotency 4-tuple UNIQUE `(tenant_id, device_id, sequence_number, external_event_id)` (not 3-tuple) so disconnects during a vendor firmware crash can replay their entire backlog without loss or double-processing.
- Status derived at heartbeat ingestion time (no background sweeper) — Phase 26 keeps it deterministic and side-effect-free; v2.5 edge agent (Phase 31) introduces the periodic poll.
- `device_events` append-only invariant enforced at the API surface (no `Update`/`Delete` on `IDeviceEventRepository`), not via DB triggers — matches the AccessControl/Visits ledger convention (ConsentAuditLog is the only DB-trigger-protected ledger because it's legally tamper-evident).
- `device_heartbeats` is intentionally mutable (per-device rollup, not a ledger) — correct semantics for a status table.
- DeviceStatus default `Online` (per row); missing heartbeat in `ListDeviceHealthHandler` renders as `Offline` — UI-SPEC "Empty state" semantics.

**Issues Resolved:**

**Issues Deferred (forward to v2.4 / v2.5):**

- **Per-device threshold override UI** (Configure button on `/devices` dashboard) — button rendered disabled with a tooltip placeholder. Defaults 60s/10% suffice for the simulator path.
- **OpenAPI client regeneration** — Phase 24/25/26 added 7+2+1 endpoints to a handwritten `DevicesApiService` that bypasses the generated OpenAPI client. Low-risk follow-up.
- **Web production Docker build skip on Windows host** — Phase 26 runs the `ng test` via `ChromeHeadlessNoSandbox` on Windows instead of the canonical Gitea runner; the per-phase Web SPA gate is green. Surfaced for transparency.
- **Subquery flake in `RunInitScripts`** (pre-existing, documented across Phases 24/25/26) — when multiple `IClassFixture<MySqlContainerFixture>` collections initialise in parallel against the shared `CE_ITEST_MYSQL` DB, MySQL throws `Subquery returns more than 1 row`. Per-collection runs are green; canonical CI gate runs the `--filter Devices` partition. Will be addressed in v2.4 by per-collection DBs.
- **Background sweep** (re-evaluate device status on a timer) — out of scope; Phase 26 derives status per-event at ingestion time. v2.5 Phase 31 edge agent introduces periodic poll.
- **Real vendor device drivers** — DOOR-R1 (Control iD, v2.5 Phase 32), DOOR-R2 (Intelbras, v2.5 Phase 33), DOOR-R3 (on-site hardware fallback, v2.5 Phase 34).

**Technical Debt Incurred:**

- **OpenAPI drift** between handwritten `DevicesApiService` and generated `services/.../devices.service.ts` — the handwritten services cover the endpoint surface; the generated client is stale on Phases 24/25/26 endpoints. Mitigation: URL paths + HTTP verbs constructed manually in the handwritten service; safe because both layers use the same `devices-api.service.ts` host binding.
- **Stale `.opencode/plugins/playwright-validate.ts` deletion in the index** — unrelated to v2.3 scope; left as-is across Phases 24/25/26.
- **`IngestHeartbeatHandler` uses `payload.OccurredAtUtc` for the gap calculation, not `DateTime.UtcNow`** (documented deviation) — the heartbeat's timestamp is the source of truth (the simulator may replay stale events from a backlog); `HeartbeatValidator` enforces a 5-minute freshness window at the API edge.
