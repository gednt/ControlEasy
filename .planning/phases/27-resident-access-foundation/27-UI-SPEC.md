## Interaction Contract — Portal Access Modal

New standalone component: `PortalAccessModalComponent` (mirror of Phase 24 `DeviceFormModalComponent`: standalone, standalone handwritten `ResidentsPortalApiService` is acceptable, opens from the residents table row action menu — and from the edit-resident modal's new "Portal access" section if the executor prefers inline — **either placement, not both, is fine; the modal itself is the contract**).

> **CONTEXT alignment:** the inline "Portal access" section on the resident create/edit flow (locked decision in 27-CONTEXT.md: *"a 'Portal Access' section on the resident create/edit flow with create/activate, suspend, revoke actions"*) matches this contract — the modal/section pair is the same surface; the table row-action entry point is the executor-equivalent way to reach it.

### State machine (one credential per resident — zero/one, never a list)

| Credential state | Badge | Badge tone | Primary action | Secondary actions |
|------------------|-------|------------|----------------|-------------------|
| No credential | "Not provisioned" | neutral | **Create portal access** (opens password form) | — |
| `Active` | "Active" | success | **Suspend access** | **Revoke access** (danger) · **Reset password** |
| `Suspended` | "Suspended" | warning | **Reactivate access** | **Revoke access** (danger) |
| `Revoked` | "Revoked" | danger* | **Create portal access** (re-provision) | — |

\* Badge tones follow the project's existing status-badge semantics (the residents table already uses `danger` tone for terminal states like Cancelled). The "destructive color reserved for destructive actions" rule applies to **buttons**; Revoked-as-badge is a status readout, not an action.

### Provision ("Create portal access") form — locked to `MustChangePassword` semantics (27-CONTEXT.md)

1. Field: **Initial password** — `ce-input type="password"` with show/hide toggle button (`aria-pressed`, eye icon), client-side minimum-length validation matching backend rule.
2. Field: **Confirm password** — mismatch error: "Passwords don't match" (field-level, `--color-danger`).
3. Helper line (muted, 12px): "The resident will be asked to change this password at first sign-in."
4. Footer: `Discard changes` (ghost) + `Create portal access` (primary, verb + noun, `[loading]` while submitting). The dismissive button is never generic "Cancel" — every interactive label is a specific verb + noun.
5. **Success step — write-once secret (Phase 24/25 raw-token pattern):** the modal swaps to a confirmation panel showing the initial password in monospace (`DM Mono`), a Copy button (clipboard API), and the warning: **"This password is shown only once. Copy it now — it will not be displayed again."** No re-fetch, no stored plaintext render. Close button: "Done".

### Suspend (reversible, no destructive styling)

- Direct action, **no confirmation modal** (suspension is reversible and takes effect on the resident's next request — the safety property is enforced server-side per RES-01, not by a UI speed bump).
- Success toast: "Portal access suspended — takes effect on the resident's next request."
- After suspension the modal state flips to `Suspended` (badge + Reactivate button) without closing.

### Reactivate

- Direct action, no confirmation. Success toast: "Portal access reactivated."

### Revoke (destructive — confirmation REQUIRED)

- Opens a small `ce-modal size="sm"` confirmation, Phase 24 remove-device pattern.
- Confirmation copy (body): "Revoke portal access for {resident name}? This permanently removes their portal credential — they can no longer sign in, and a new credential would need to be provisioned with a new password. This cannot be undone."
- Footer: `Keep access` (ghost) + `Revoke access` (danger). Button is `[loading]` while submitting. On success: modal state flips to `Revoked` + toast "Portal access revoked."

### Reset password (Phase 17/18 machinery extension — no new pattern)

- "Reset password" runs the TenantAdmin reset endpoint; on success it shows the **same write-once password panel** as provisioning, with the same shown-only-once warning, and toast "Password reset — the resident must change it at next sign-in."
- The UI never displays the current password, and there is no "resend" — repeated resets are new resets.

### Visibility & permissions

- Action menu "Portal access" item and all modal actions render only when `auth.hasPermission('Residents.Write')` (same `canWrite` computed the page already uses) — i.e., TenantAdmin per RES-01.
- Never render the credential status or any password material to non-privileged users.

## Accessibility Contract

- All Portal Access actions are real `<button type="button">` inside `ce-button` (keyboard reachable, `focus-visible` outline via existing component styles).
- The password show/hide toggle is a labeled button with `aria-pressed`, not a bare icon.
- The write-once password uses `aria-live="polite"` on the confirmation panel so screen readers announce issuance; the Copy button announces itself by visible label, not icon-only.
- Status badges carry their text content (no color-only signalling) — `ce-badge` renders string content already.
- Toasts flow through `ce-toast` / `ToastService` (`aria-live="polite"`, dismissible) per the Phase 26 pattern.
- Modal focus trap + Escape-to-close come from `ce-modal`; destructive confirmations are NOT dismissed by backdrop click during in-flight submit (follow existing `onModalOpenChange` guard pattern from residents page).
